# Snake

Игра «Змейка» на WPF (.NET 10). Разработка идёт автономными прогонами команды `/goal`.

## Документы

| Файл | Что в нём |
|---|---|
| `REQUIREMENTS.md` | Требования FR/NFR и Definition of Done. Источник истины. |
| `tracker.md` | Статус задач T01 … T25 по этапам. |
| `completion-conditions.md` | Готовые условия `/goal` на каждый этап. |
| `verify.ps1` | Единственная машинная проверка DoD. |

## Главное правило проекта

**DoD формулируется только машинно-проверяемым.**

Причина: готовность оценивает отдельная модель, которая видит **только текст разговора**.
Она не запускает тесты и не читает файлы. Поэтому пункт «приложение работает корректно»
бесполезен — модель поверит словам. Доказательством служит вывод команды и её код выхода.

Как применять:

- Любой новый критерий готовности должен сводиться к команде с кодом выхода.
- Если критерий нельзя так выразить — он идёт в раздел 7.3 требований, в ручную приёмку,
  и в условие `/goal` не попадает.
- Нельзя заменять проверку текстом «я проверил». Нужно запустить команду, чтобы её вывод
  оказался в разговоре.

## Проверка

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File ./verify.ps1 -Stage <N> -MinTests <M>
```

`-Stage 0` — все этапы. Код выхода 0 означает, что машинный DoD выполнен.

## Защищённые файлы

`verify.ps1`, `Directory.Build.props`, `REQUIREMENTS.md` сравниваются с git-тегом `0.0.0`.
Скрипт падает, если они изменились.

Причина: самый короткий путь к зелёной проверке — ослабить саму проверку. Если требования
действительно надо поменять, это делает человек и переносит тег.

## Структура кода

- `src/Snake.Core` — вся логика игры. **Не знает про WPF**: ни окон, ни отрисовки,
  ни `Dispatcher`, ни клавиатуры. Это проверяется автоматически.
- `src/Snake.Wpf` — интерфейс. Только отрисовка, ввод и таймер тиков.
- `tests/Snake.Core.Tests` — тесты логики.

## Доменная модель: облегчённый DDD

В проекте один агрегат, поэтому берём из DDD только то, что здесь работает.

**Единый язык.** Имена в коде берутся из глоссария (раздел 2 `REQUIREMENTS.md`).
Один термин — одно имя, во всём коде и в именах тестов. Синонимы не заводим:
если в требованиях «клетка», то в коде `Cell`, а не `Point`, `Square` или `Position`.

| Термин в требованиях | Имя в коде |
|---|---|
| Поле | `Board` |
| Клетка | `Cell` |
| Змейка | `Snake` |
| Голова, хвост | `Head`, `Tail` |
| Тик | `Tick` |
| Направление | `Direction` |
| Еда | `Food` |
| Свободная клетка | `FreeCell` |
| Проход сквозь стену | `Wrap` |
| Уровень сложности | `Difficulty` |
| Счёт | `Score` |
| Рекорд | `HighScore` |

Новый термин сначала появляется в глоссарии требований, потом в коде. Не наоборот.

**Value objects.** `Cell`, `Direction` и подобные — неизменяемые, сравниваются по значению,
не имеют идентичности. Для `Cell` это `readonly record struct`.

**Корень агрегата.** Партия — один агрегат, его корень — `Game`. Менять состояние партии
можно только через методы `Game`. Наружу состояние отдаётся только для чтения: нельзя
получить список клеток змейки и дописать в него клетку. Инварианты (длина, положение еды,
статус партии) держит корень, а не вызывающий код.

**Чистый домен.** `Snake.Core` не знает про файлы, время, окна и ввод. Это уже NFR-01
и проверяется автоматически.

**Чего в этом проекте не делаем.** Репозиториев, фабрик, доменных событий, отдельных
слоёв Application и Infrastructure. Агрегат один, границы контекста одни — эти слои
добавят код, но не добавят ясности. Если появится причина их завести, сначала записываем
причину сюда.

## Комментарии: их нет

**В C#-коде комментариев не пишем.** Код объясняет себя сам: именами типов, методов,
переменных и констант.

Если тянет написать комментарий — это сигнал, что код непонятен. Вместо комментария:

- выделить кусок в метод с говорящим именем;
- заменить число или строку на именованную константу;
- переименовать переменную;
- разбить длинный метод.

**Единственное исключение.** Правило неочевидно и выглядит в коде как ошибка. Тогда
одна строка с ответом на вопрос «почему» и номером требования. Имена отвечают на вопрос
«что», но не могут объяснить «почему правило именно такое».

Два места в этом проекте, где исключение оправдано:

- **FR-12** — вход в клетку, которую хвост освобождает на этом же тике, разрешён.
  Без пояснения читатель примет это за пропущенную проверку столкновения.
- **FR-15** — разворот сравнивается с последним направлением в очереди, а не с текущим
  направлением змейки. Выглядит как лишнее усложнение, но без этого змейка
  разворачивается сама в себя.

**Запрещено в любом случае:**

- комментарий, пересказывающий код (`// увеличиваем счёт`);
- закомментированный код — для истории есть git;
- `TODO` и `FIXME` без номера задачи из `tracker.md`;
- XML-doc, который повторяет имя метода другими словами.

**Тесты — это документация.** Имя теста должно читаться как утверждение о поведении
и называть требование. Тогда комментарии в тестах тоже не нужны.

Правило касается только C#. На `verify.ps1`, XAML и markdown оно не распространяется.

## Правила кода

- Шаг игры — функция «состояние + ввод → новое состояние», без побочных эффектов.
- `Random` передаётся снаружи. В тестах — с фиксированным зерном.
- Системное время в `Snake.Core` не используется. Тики вызываются явно.
- Хранилище скрыто за интерфейсом. Тесты не трогают файловую систему.
- Предупреждения компилятора приравнены к ошибкам.
- Поля enum, которые сохраняются в JSON, пишутся строкой, а не числом.
- Магические числа выносятся в именованные константы: размер поля, длина змейки,
  интервалы тика, множители очков.
- Мёртвый код не остаётся: неиспользуемые методы, поля и `using` удаляются.

## Если задача не поддаётся

Создать файл `BLOCKED` в корне репозитория с причиной и остановиться. Прогон `/goal`
завершится. Файл `BLOCKED` в `.gitignore` не входит — он должен быть виден.
